## 1. 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│ 接入层 dag-demo（示例工程）                                    │
│  业务执行器(@Component) · 固定流程定义注册 · 调用方示例          │
└──────────────────────────┬───────────────────────────────────┘
                           │ 调用进程内 API
┌──────────────────────────▼───────────────────────────────────┐
│ 引擎核心 dag-core（Spring Boot Starter）                      │
│  API 面      DagEngine：submit / confirm / fail / cancel /    │
│              retry / resume / forceFinalize / getTask          │
│  服务层      TaskService · ConfirmService · GraphValidator     │
│  运行时      Scheduler · NodeExecutor · NodeInspector ·        │
│              TaskStateMachine · FallbackScanner                │
│  基础设施    HandlerRegistry · LockManager · TaskStore/NodeStore│
└──────┬─────────────────────────────┬─────────────────────────┘
       │ MySQL（3 表，CAS 权威）      │ Redis Cluster（Redisson 锁）
       ▼                             ▼
   task_instance / node_instance /   dag:node:{id} 锁
   flow_definition                   （watchdog 自动续期）
```

- **单机内嵌**：引擎以 starter 形式嵌入业务服务，调度器、扫描器随应用启动
- **多实例防重**：所有状态流转以 MySQL CAS 条件更新为权威，Redis 锁负责执行权与中断判定
- **MySQL 5.6 约束**：无 `FOR UPDATE SKIP LOCKED` → 候选领取 = 普通查询 + CAS 领取；无 JSON 类型 → 图/结果以 TEXT 存储

## 3. 核心组件职责

| 组件 | 职责 | 关键约束 |
|---|---|---|
| DagEngine | 进程内门面，封装全部 API | 业务方唯一入口 |
| GraphParser / GraphValidator | graph_json → GraphDsl；校验可执行性 | 校验失败拒绝落库（400） |
| HandlerRegistry | 按 handler 名称从容器取 Bean | handler = @Component 名称；未找到即校验失败 |
| Scheduler | 周期扫描 PENDING 且前驱全 SUCCESS 节点 → 提交执行 | 每实例独立运行，重复扫描无害 |
| NodeExecutor | 单节点执行：tryLock → CAS PENDING→RUNNING → 调 handler → 三路分发 | 锁内执行；结果 SUCCESS/FAILED/WAIT_CONFIRM |
| NodeInspector（统一巡检） | 对 RUNNING 节点 tryLock：抢到 = 执行中断 → CAS 回 PENDING；抢不到 = 执行器存活 → 超时判定 FAILED(time_out=1) | 合并原超时/异常扫描；只处理 RUNNING |
| TaskStateMachine | 任务收敛：全 SUCCESS→SUCCESS；任一 FAILED→FAILED（CAS 一次） | 收敛兜底扫描防丢失 |
| TaskService | 提交与人工控制操作 | 各操作带状态前置校验 |
| ConfirmService | confirm/fail 确认（进程内） | 仅 WAIT_CONFIRM 生效，CAS 幂等 |
| LockManager | Redisson RLock；未配置 Redis 降级 JVM 本地锁 | 多实例建议开启 Redis |

## 4. 关键机制设计

### 4.1 调度与领取（CAS 防重）

调度器每轮（默认 1s）：

1. 查询候选：`state='PENDING'` 且**前驱全 SUCCESS** 的节点（普通 SELECT，MySQL 5.6 无 SKIP LOCKED）
   - 前驱校验（子查询）：`NOT EXISTS(上游节点且 state != 'SUCCESS')`
   - 批量上限 `dag.scheduler.batch-size`（默认 100）
2. 对每个候选执行**领取**（两段式）：
   - **① 先 tryLock**（`dag:node:{nodeId}`，watchdog 自动续期）→ 拿到锁 = 获得执行权
   - **② 再 CAS**：`UPDATE node_instance SET state='RUNNING', started_at=NOW() WHERE id=? AND state='PENDING'`，影响行数 = 1 才算领取成功
   - ② 失败（已被其他实例/取消抢占）→ 释放锁，跳过
3. 领取成功后提交执行线程池，由 NodeExecutor 在锁内执行

> 顺序说明：**先拿锁再 CAS**。锁是执行权令牌，CAS 是状态转换；CAS 失败即释放令牌，无悬挂；"RUNNING 无锁 = 中断"的判定语义因此成立（异常扫描 §4.5）。

### 4.2 推进机制（push 主路径 + pull 兜底扫描）

**主路径（事件驱动 push，进程内即时触发）**：节点进入终态（SUCCESS）后，状态机在同一进程内即时评估其后继：

1. 取该节点的直接后继（DAG 邻接表）
2. 逐个判断"后继的所有前驱是否已 SUCCESS"：
   - 满足 → 立即走统一领取（§4.1 tryLock + CAS）并提交执行线程池
   - 不满足（join 场景下其他前驱未完成）→ 跳过；最后一个前驱完成时评估自然通过 → 触发
3. 节点终态为 FAILED → 收敛任务 FAILED，不触发下游

**兜底路径（pull 扫描，周期）**：调度器周期扫描"PENDING 且前驱全 SUCCESS"的节点 → 走同一统一领取。正常时 push 已即时触发，扫描器几乎无事；**进程在"终态写入 → 触发下游"之间崩溃时，推进丢失，由重启后的兜底扫描捡回**——这是纯 push 必须配兜底扫描的原因。

**双路径共存**：两条路径都汇合到同一领取方法（tryLock + CAS `PENDING→RUNNING`）：

- **去重**：重复触发时 CAS 只成功一次——去重本就是多实例防重的一部分（§4.8），无需额外组件
- **丢失补偿**：崩溃丢失的推进由重启后的兜底扫描补上——补偿职责由扫描天然承担，无需消息补偿
- **不需要消息队列**：推进是进程内直接调用（终态写入后同步评估下游），不跨进程；MQ / 消息去重 / 消息丢失补偿均为跨进程消息架构所需，本设计不需要

**崩溃安全**：状态以 DB 为唯一事实；崩溃重启后，兜底扫描重新评估全部 PENDING 节点，任何丢失的推进都会被捡起。

**与 4.1 的关系**：两条路径决定"尝试触发哪些节点"，4.1 的统一领取决定"由谁执行成功"（锁 + CAS 防重）。

### 4.3 异步回调（WAIT_CONFIRM）

1. handler 返回 `ExecutionResult.pending()` → 节点 CAS `RUNNING→WAIT_CONFIRM` → **释放锁**
2. 业务方异步任务完成后调 `DagEngine.confirm(nodeId, result)`（或 `fail`）
   - CAS：`UPDATE node_instance SET state=?, result=? WHERE id=? AND state='WAIT_CONFIRM'`，影响行数 0 即幂等忽略（重复/晚到回调）
3. 确认成功 → 进入终态，调度器下一轮按 4.2 继续推进
4. **resume**：仅 WAIT_CONFIRM 节点，CAS `WAIT_CONFIRM→PENDING`，重新入调度

> WAIT_CONFIRM 期间：无锁、无超时；异常扫描只处理 RUNNING，不会误重置。

### 4.4 超时扫描（平台统一超时）

- 配置 `dag.node.timeout`（默认 60s），同步节点共用，节点不自定义
- SQL：`SELECT ... WHERE state='RUNNING' AND started_at < NOW() - INTERVAL ? SECOND`
- 命中 → CAS `RUNNING→FAILED`（`time_out=1, result='timeout'`）→ 触发任务收敛
- 竞态：与执行完成/异常扫描并发时，CAS 谁先成功谁生效，安全

### 4.5 异常扫描（Redis 锁判定执行中断）

> 实现层：§4.4 超时扫描 + §4.5 异常扫描合并为统一巡检器 `NodeInspector`（一次 tryLock 判定两件事），见 04 §2.4 / 05 §3.5。

- 前提：执行器持有 `dag:node:{nodeId}` 锁（watchdog 每 10s 续期，租期 30s）；**服务挂掉 → 锁自动过期释放**
- 判定：对 RUNNING 节点 `tryLock(0)`：
  - **抢到锁 = 原持有者已死** → 保持持锁 → CAS `RUNNING→PENDING`（清 started_at/result/time_out）→ 释放锁 → 重新入调度
  - **抢不到 = 执行器还活着** → 跳过（交由超时扫描判断业务超时）
- 与超时扫描的分工：锁在 → 超时扫描判 TIMEOUT；锁不在 → 异常扫描重置重执行
- 边界情况：JVM 活但 Redisson 客户端异常导致锁误释放 → 极小概率，节点被重置重执行（at-least-once，handler 幂等兜底）

### 4.6 任务状态收敛

| 触发 | 收敛动作 |
|---|---|
| 节点 → SUCCESS | 检查任务全部节点 SUCCESS → CAS `task RUNNING→SUCCESS` |
| 节点 → FAILED | CAS `task RUNNING→FAILED`（仅一次，不覆盖 SUCCESS/CANCELLED） |
| 用户 cancel | CAS `task RUNNING→CANCELLED`，节点按 §4.7 收敛 |

- **收敛一致性（短事务）**：节点终态写入 + 任务收敛判断/更新放同一短事务（CAS 更新 node 行 → 检查全节点 → 收敛 task 行），原子提交，正常路径不丢失收敛；兜底扫描仅作保险（提交前崩溃则节点终态未生效，重新处理即可）
- 任务 FAILED/CANCELLED 后：调度器领取时检查任务状态，不再领取新节点；已 RUNNING 节点自然结束

### 4.7 人工控制操作（均有状态前置校验）

| 操作 | 前置校验 | 动作 |
|---|---|---|
| retry CONTINUE | 任务 FAILED | 非 SUCCESS 节点（FAILED/WAIT_CONFIRM）→ CAS 回 PENDING 并清 time_out/result；任务 CAS FAILED→RUNNING |
| retry RESTART | 任务 FAILED | 全部节点 → PENDING 清空结果；任务 CAS FAILED→RUNNING |
| cancel | 任务 RUNNING | 任务 CAS → CANCELLED；PENDING 节点批量 → CANCELLED；RUNNING 同步节点 → CANCELLED（执行结果晚到 CAS 失败自动忽略）；WAIT_CONFIRM → CANCELLED（晚到回调忽略） |
| resume | 节点 WAIT_CONFIRM | CAS → PENDING |
| forceFinalize（运维） | 任意非终态 | 任务/节点 CAS → 指定终态（兜底出口） |

> retry 语义说明：CONTINUE 重置"所有未成功节点"（含 WAIT_CONFIRM，因任务整体重跑，等待中的分支也重新执行）；若业务需要保留已等待确认的结果，可调整该规则（待确认，默认按上述实现）。

### 4.8 多实例防重总览

| 层面 | 机制 |
|---|---|
| 领取执行权 | Redisson 锁（tryLock + watchdog 续期） |
| 领取状态 | CAS `PENDING→RUNNING` |
| 终态写入 | CAS（仅匹配前置状态） |
| 任务收敛 | CAS `RUNNING→终态` |
| 回调确认 | CAS（仅 WAIT_CONFIRM） |
| 异常判定 | 锁可抢 = 执行中断 |
| 候选查询 | 普通 SELECT（MySQL 5.6 无 SKIP LOCKED） |

### 4.9 Redis 降级策略

- 未配置/不可用：LockManager 降级 JVM 本地锁（ReentrantLock，按 nodeId 维度）
- 降级后果：异常扫描无法跨实例判定 → 异常扫描自动关闭；多实例防重仍由 CAS 保证；崩溃恢复依赖超时收敛（同步）与 WAIT_CONFIRM 持久化（异步）
- 约束：**多实例生产环境必须开启 Redis**；单实例/demo 可无 Redis

## 5. 数据访问与事务边界

- 无长事务：所有状态流转为单条 CAS UPDATE，天然原子
- 提交任务 = 短事务：插入 task_instance + 批量插入 node_instance + 流水（三表一致）
- 节点终态 + 任务收敛 = 短事务原子提交（见 05 §3.6），正常路径不丢收敛；提交前崩溃则节点终态未生效，由巡检/兜底重新处理
- 连接与重试：JdbcTemplate 直连；DB 抖动由扫描器退避重试（见 07）

## 7. 线程模型

| 线程 | 职责 | 说明 |
|---|---|---|
| 调度线程（单） | 扫描候选 → 领取 → 提交执行线程池 | ScheduledExecutor，interval 可配 |
| 执行线程池 | 锁内执行 handler | ThreadPoolExecutor，线程数可配 |
| 巡检线程 | 巡检 RUNNING：tryLock 判中断 + 超时判定（统一） | 独立定时线程 |
| 调用方线程 | confirm/fail/cancel/retry 等 API | 快路径，直接 CAS |
